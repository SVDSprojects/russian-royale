# Архитектура и развитие

## Граница доверия

Клиент передаёт намерение: готовность, голос, ответ. Секретная роль, выбранная тема, время и результаты находятся только на сервере. Игровые запросы проверяют сессию, членство закрытого сервера, участие в текущем раунде, этап и право ведущего. Роль администратора берётся из БД на каждом запросе; поля `role` при регистрации не дают дополнительных прав.

Cookie содержит случайный токен, в БД — его SHA-256. Пароли — scrypt со случайной солью. Изменяющие запросы проверяют Origin/Sec-Fetch-Site. HTTP-ответы API не кэшируются, секреты не передаются в URL и SSE. Пользовательский текст отображается React как текст, HTML не исполняется. Загружаемые растры заново декодируются; SVG не принимается. Административные операции журналируются.

Уникальный ключ `(session_id,voter_id)` не позволяет голосовать дважды. Результаты имеют `(session_id,user_id)`; начисление опыта выполняется вместе с сохранением результата в транзакции. Запуск раунда возможен только из лобби. Процесс Node один, операции SQLite синхронные, изменения игры без `await` внутри транзакции — это сериализует конкурирующие игровые действия. При нескольких Node-процессах данная схема управления SSE/таймерами больше не является достаточной.

## Данные

Таблицы аккаунтов/контента: `users`, `sessions`, `categories`, `rules`, `exercises`, `lessons`, `progress`, `answers`, `lesson_completions`, `teacher`, `audit_log`, `seed_metadata`, `schema_migrations`.

Мультиплеер: `servers`, `server_members`, `invites`, `rooms`, `room_members`, `game_sessions`, `game_players`, `game_votes`, `game_results`, `messages`.

Снимок темы находится в `game_sessions`, отдельно от редактируемого правила. Внешнего ключа к удаляемому учебному правилу нет. История ответов сохраняет текст задания/ответа/темы; ссылки на удалённые упражнения становятся NULL. Удаление сервера после окончания игр сохраняет игровые сессии и результаты.

Сценарий урока хранится JSON-массивом блоков с валидацией типов и ссылок на задания. Это намеренно гибкая часть контента; остальные связи нормализованы. Демонстрационные записи создаются один раз, маркер заполнения независим от наличия контента. Отсутствие материала после удаления — нормальное состояние.

## Синхронизация

`GET /api/events` — авторизованное постоянное SSE-соединение. Его события содержат только `{}`; браузер заново запрашивает нужные API. Обновления объединяются клиентом за 75 мс, резервная сверка раз в 12 секунд. Heartbeat раз в 15 секунд проверяет, что сессия ещё действительна. Автоматическое переподключение — средствами EventSource.

RoomView выдаёт только собственную роль. До результатов у шпиона нет поля `topic`, ID правила или чужих ролей. Время — абсолютный серверный deadline, UI оценивает смещение часов по `serverNow`. Серверный тик выполняется каждую секунду и дополнительно перед критическими действиями. Перезапуск не продлевает истёкшие этапы.

Статус участника комнаты основан на последних запросах к комнате. Ведущий передаётся после 45 секунд без активности, либо сразу при явном выходе, если другой игрок присутствует. Все отключившиеся игроки остаются участниками текущего раунда: их молчание учитывается как отсутствие голоса.

## Ограничения текущей реализации

- SQLite, один процесс, один постоянный диск. Это тестовая платформа, а не подтверждённая высоконагруженная инфраструктура.
- Лимиты и online-presence в памяти процесса; они сбрасываются при перезапуске. Данные игры и сессии входа сохраняются.
- История интерфейса ограничена последними 200 действиями, списки админки/рейтинга ограничены. Полная история в базе; постраничный API нужен для дальнейшего роста.
- Нет email verification/reset, удаления собственного аккаунта и интерфейса жалоб. Перед открытым запуском для широкой аудитории их необходимо добавить.
- Доверенный редактор может менять учебный контент. У участника с редакторскими правами больше сведений о библиотеке; роли редакторов следует давать только команде проекта.
- Секретная тема выбирается из опубликованной библиотеки. Одно правило не обеспечивает игровой интриги; это демонстрация работоспособности.
- Статический хостинг или ephemeral-диск без persistent volume для этой архитектуры не подходят.

## Следующие этапы

1. **Инфраструктура:** выделить репозитории данных из Express-обработчиков; реализовать адаптер PostgreSQL. Перенести миграции, транзакции и ограничения, написать тесты на реальной PostgreSQL. Для Supabase добавить Auth и таблицы профилей, RLS на пользовательские данные, service-role доступ только серверным функциям, Realtime для публичных состояний и Storage с проверкой загрузок. Не переносить секретные игровые таблицы в подписку всех участников. При нескольких узлах применять блокировки/CAS-версию комнаты, общий pub/sub и планировщик таймеров.
2. **Игровой движок:** добавить `mode` в комнаты/сессии, отделить общий lifecycle (лобби, активна, закончена) от специфических фаз движка. Убрать обязательный `spy_id` из общей сессии в модуль Spy. Каждый модуль предоставляет `validateSettings`, `start`, `applyAction`, `onDeadline`, `projectForUser`, `results`. Сначала «Мафия» с приватными ночными действиями и тестами, затем «Бункер» и карточный «Дурак»; далее шесть остальных режимов. Карточки на сайте сейчас описывают план, а не готовые движки.
3. **Социальные функции:** заявки в друзья, настройки приватности, приглашения в конкретную комнату, управление участниками, жалобы, блокировки. Роли сервера и глобальные роли остаются разными сущностями.
4. **Обучение:** журнал попыток уже существует; на его основе добавить интервалы повторения, очереди ошибок, изученные слова и сложность. Материал всегда берётся из БД.
5. **ЕГЭ:** нормализованные `exam_variants`, `exam_items`, `exam_attempts`, `exam_answers`, `essay_reviews`. Схема оценивания версионируется, сохраняется вместе с попыткой. Автосохранение, таймер и продолжение после перезагрузки. PDF/DOCX проходят импорт в черновик и ручную проверку. Не придумывать официальный перевод баллов, не выдавать автоматическую оценку сочинения за экспертную.
6. **Качество:** тестирование Safari/iOS/Android на физических устройствах, плохой сети и длительных партиях; нагрузка с дисковой БД и несколькими комнатами; аудит доступности, резервное копирование и сценарий восстановления.
